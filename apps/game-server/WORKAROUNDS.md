# Workarounds & future cleanups — `apps/game-server`

Things that are intentional for now but should be revisited / removed later. Add an entry when you leave a temporary shim, a deferred migration, or anything a future reader might mistake for a permanent decision. Keep entries short and link the code.

## Engine isolation covers only the `move` path (`app/services/engine-runner.ts`, `app/routes/gameplay.ts`)

Engines run in-process via dynamic `import()`; a synchronous infinite loop in any engine method wedges the whole game-server event loop (the 2026-08-09 outage). As a first step, only the player-facing **`move`** call runs inside a `worker_thread` with a hard timeout (`engineRunner.call`, default 10s via `ENGINE_CALL_TIMEOUT_MS`) — a runaway `move` is terminated and fails that one request instead of hanging the server. The other engine entry points (`init`, `dropPlayer`, `replay`, `logSlice`, `afterMove`'s `scores`/`currentPlayer`/etc.) still run on the main thread and can still wedge it. The safety nets for those: the external **watchdog** (`scripts/watchdog.ts`, restarts an app whose `/health` stops answering — its timeout catches even a fully blocked loop) and the in-process **event-loop guard** (`@bgs/utils/watchdog`, exits a worker whose loop is severely lagging so PM2 restarts it; note a _fully_ blocked loop can't run its own `process.exit()`, so the guard covers lag, the watchdog covers the hard wedge). Main-thread calls are at least **attributed** now: they go through `trackedEngine` (`app/services/engine-call-context.ts`), which keeps a module-level "current engine call" context (game, method, acting player, move) that the event-loop guard logs when it fires, and logs a `slowEngineCall` warning for any call over `SLOW_ENGINE_CALL_MS` (default 2s) — so a lag/wedge names its culprit, though a fully blocked loop still can't log its own context. Full isolation = route every engine call through the runner (or a worker pool / separate engine pod). Revisit when extending coverage.

## ~~Short-game per-move increment credited in the route~~ — RESOLVED

**Removed**: the `/move` route no longer pre-credits `+timePerMove` and the cross-layer `incrementCredited` flag is gone. The increment now lives entirely in `afterMove` (`app/services/game.ts`, `creditIncrement`): the mover of a real saved move (`lastMove` set — route and bot moves) is credited exactly once, whether they leave the current-player set or stay in it (repeat mover, #12); callers without `lastMove` (replays, admin data edits, drop/quit) get no increment. History: for short games (`timePerMove <= 15min`) the route used to add `+timePerMove` before calling `afterMove` ("add time back every move", the original #12 fix); `afterMove` skipped its own increment for route moves via `incrementCredited` (the #311 fix for the resulting double-credit of alternating movers). The split crediting was load-bearing in both directions until the consolidation into `afterMove`.

## Listen host: default `127.0.0.1`, prod binds `::1` (`app/config/env.ts`)

Same as `apps/api` (`apps/api/WORKAROUNDS.md`): `env.listen.host` defaults to `127.0.0.1` for local dev / multi-instance (`scripts/instance-ip.sh`); prod sets `listenHost=::1` and the nginx upstream (`gaia_game_server`) dials `::1:50803`. Override via the `listenHost` env var; keep server bind and the nginx upstream on the same address family.
